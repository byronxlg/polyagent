# Database Guide

This file provides guidance for database setup and management in the PolyAgent project.

For general project information, see [../CLAUDE.md](../CLAUDE.md)

## Database Setup

### Using Docker (Recommended)

The project uses PostgreSQL in a Docker container for development.

```bash
cd database
docker-compose up -d
```

This starts:
- PostgreSQL 16 on port 5432
- Database name: `polyagent`
- Username: `postgres`
- Password: `postgres`

### Connecting to the Database

**Connection String:**
```
postgresql://postgres:postgres@localhost:5432/polyagent
```

**Environment Variable (.env):**
```bash
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/polyagent
```

### Database Management Commands

```bash
# Start database
docker-compose up -d

# Stop database
docker-compose down

# View logs
docker-compose logs -f

# Connect with psql
docker-compose exec postgres psql -U postgres -d polyagent

# Restart database
docker-compose restart

# Remove database (WARNING: deletes all data)
docker-compose down -v
```

## Database Schema

See `docs/datamodel.mmd` for the complete entity-relationship diagram.

### Core Tables

**principals** - Identity accounts (human, ai_agent, system)
**simulations** - Simulation environments
**models** - LLM model definitions with costs
**agents** - Agent instances
**tasks** - Work items for agents
**agent_tasks** - Junction table linking agents to tasks they work on
**messages** - Agent-to-agent communication
**tools** - Available tools (system and custom)
**agent_tools** - Junction table controlling tool access
**transactions** - Immutable credit ledger
**agent_model_usage** - LLM API call tracking
**agent_tool_usage** - Tool invocation tracking

### Key Relationships

- Agent → Principal (one-to-one)
- Agent → Model (many-to-one)
- Agent → Simulation (many-to-one)
- AgentTask → Task (many-to-one)
- AgentTask → Agent (many-to-one)
- AgentModelUsage → AgentTask (many-to-one, optional)
- AgentToolUsage → AgentTask (many-to-one, optional)

## Schema Migrations

The project uses Alembic for schema migrations. See [../polyagent/CLAUDE.md](../polyagent/CLAUDE.md#database-migrations) for migration commands.

### Migration Workflow

1. Update models in `src/models.py`
2. Generate migration: `uv run alembic revision --autogenerate -m "description"`
3. Review migration in `alembic/versions/`
4. Apply migration: `uv run alembic upgrade head`

### Migration Best Practices

- **Always review autogenerated migrations** - Alembic may miss data transformations
- **Add data migrations when needed** - Use `op.execute()` for data changes
- **Test migrations on a copy** - Especially when modifying existing tables
- **Use descriptive names** - Help future developers understand changes
- **Never edit applied migrations** - Create new migration to fix issues

## Data Types

### PostgreSQL → SQLAlchemy → Python

| PostgreSQL | SQLAlchemy | Python | Notes |
|------------|------------|--------|-------|
| `INTEGER` | `Integer` | `int` | Primary keys, IDs |
| `VARCHAR` | `String` | `str` | Text fields |
| `TEXT` | `Text` | `str` | Long text |
| `NUMERIC(20,10)` | `Numeric(20,10)` | `Decimal` | Money, precise decimals |
| `BOOLEAN` | `Boolean` | `bool` | True/False |
| `TIMESTAMP` | `DateTime` | `datetime` | UTC timestamps |
| `JSON` | `JSON` | `dict` | Structured data |

### Important Type Notes

- **Use `Decimal` for money**: Never use `float` for credit amounts
- **Always use UTC**: Store timestamps in UTC, convert to local in UI
- **Nullable by default**: Use `nullable=False` only when required
- **String lengths**: Specify when known (e.g., `String(255)`)

## Database Queries

### Using SQLAlchemy

The project uses SQLAlchemy 2.0 with type hints:

```python
from sqlalchemy import select
from src.models import Agent

# Query all agents
stmt = select(Agent).where(Agent.is_running == True)
agents = session.execute(stmt).scalars().all()

# Query with join
stmt = select(Agent).join(Agent.model).where(Model.name == "GPT-4")
agents = session.execute(stmt).scalars().all()
```

### Common Patterns

**Get by ID:**
```python
agent = session.get(Agent, agent_id)
```

**Filter and order:**
```python
stmt = select(Task).where(Task.is_completed == False).order_by(Task.deadline)
tasks = session.execute(stmt).scalars().all()
```

**Count:**
```python
from sqlalchemy import func
stmt = select(func.count(Agent.id))
count = session.execute(stmt).scalar()
```

**Aggregate:**
```python
stmt = select(func.sum(Transaction.amount)).where(Transaction.to_agent_id == agent_id)
total = session.execute(stmt).scalar() or Decimal(0)
```

## Performance Considerations

### Indexing

Important indexes already created:
- Primary keys (automatic)
- Foreign keys (automatic in PostgreSQL)
- `agent_model_usage.agent_task_id` (manual index)
- `agent_tool_usage.agent_task_id` (manual index)

### Query Optimization

- **Use `select()` instead of `Query`**: SQLAlchemy 2.0 style
- **Eager load relationships**: Use `selectinload()` to avoid N+1 queries
- **Limit results**: Use `limit()` for pagination
- **Use indexes**: Query on indexed columns when possible

### Connection Pooling

SQLAlchemy handles connection pooling automatically:
- Default pool size: 5 connections
- Max overflow: 10 additional connections
- Connections recycled after use

## Backup and Restore

### Backup Database

```bash
# Backup to file
docker-compose exec postgres pg_dump -U postgres polyagent > backup.sql

# Compressed backup
docker-compose exec postgres pg_dump -U postgres polyagent | gzip > backup.sql.gz
```

### Restore Database

```bash
# Restore from file
cat backup.sql | docker-compose exec -T postgres psql -U postgres polyagent

# Restore from compressed
gunzip -c backup.sql.gz | docker-compose exec -T postgres psql -U postgres polyagent
```

## Troubleshooting

### Connection Refused

**Problem:** Can't connect to database

**Solutions:**
- Check Docker is running: `docker ps`
- Check database is running: `docker-compose ps`
- Check port 5432 isn't in use: `lsof -i :5432`
- Restart database: `docker-compose restart`

### Migration Conflicts

**Problem:** Alembic migration conflicts

**Solutions:**
- Check current revision: `uv run alembic current`
- View migration history: `uv run alembic history`
- Manually resolve conflicts in migration files
- Use `alembic stamp <revision>` to mark as applied without running

### Slow Queries

**Problem:** Database queries are slow

**Solutions:**
- Check query with `EXPLAIN ANALYZE`
- Add indexes on frequently queried columns
- Use `selectinload()` for relationships
- Limit result sets with pagination

## Development vs Production

### Development
- Docker container on localhost
- Username/password in .env file
- Connection pooling with small pool
- Query logging enabled

### Production (Future)
- Managed PostgreSQL service (e.g., RDS, Cloud SQL)
- SSL/TLS connections required
- Larger connection pool
- Automated backups
- Read replicas for scaling
- Query logging to monitoring service
